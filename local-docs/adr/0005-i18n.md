# ADR-0005: Internationalisation (English + Urdu) via react-i18next

## Status
**Accepted (2026-08-04)** — implementation delivered per plan; owner approved Option A (accept extraction + kept the Urdu file as a machine draft the owner reviews and corrects). Accepted deviations from the original plan: (1) i18next v26's `initImmediate` config option was omitted (removed in v26); (2) typed-key augmentation via `i18next.d.ts` was dropped (v26's type resolution differs from the plan's v23 assumption — keys remain plain strings, verified at runtime); (3) switcher label displays the currently-active language rather than the target language (fixes an ambiguous-click bug when `ur.json` shares strings with `en.json`); (4) `ur.json` ships as a machine-authored Mixed-register draft pending owner review (see D27, and `docs/design/i18n-strings.md` reconciliation table). Original status: Proposed (2026-08-04) — implementation plan in [docs/design/i18n-plan.md](../design/i18n-plan.md)

## Context
The portal must offer its UI chrome in English and Urdu. Owner decisions (final, 2026-08-04):

1. **Languages**: English (`en`) + Urdu (`ur`). **No layout mirroring** — the layout stays LTR; Urdu text renders naturally through Unicode bidi inside elements.
2. **Library, not hand-rolled** — owner explicitly chose a library despite bundle cost. **Bundle size deprioritized by owner 2026-08-04**; the D24 guard band will be mechanically reset after implementation, with no mitigation work.
3. **Scope: UI chrome only** — nav, buttons, headings, table headers, form labels, validation messages, empty states, aria-labels. NOT data values, NOT date formats (DD/MM/YYYY stays), NOT CSV content.
4. **Switcher in the header**; language persisted in localStorage under its **own key** (the auth session envelope is H7-locked and must not be touched); default is English on first visit — no browser-language detection.
5. **Owner authors the Urdu translations himself** from a string table the team delivers; the app ships English-complete, with Urdu falling back to English for any missing key.

Technical drivers: React 18.3.1 + Vite 6, TypeScript strict (0 errors gate), single JS chunk (Iter 4.4 decision), 119 vitest tests that assert English UI strings, bundle-size regression test in `tests/regression/bundle-size.test.ts` (band 243.5–246.5 kB gzip via `zlib.gzipSync`, Node `>=24 <25`). H9 (no unnecessary comments) and H10 (simplest thing that works) apply throughout.

## Options Considered

Per owner decision the choice is a library; hand-rolled is recorded for completeness only.

1. **i18next + react-i18next** (recommended)
   - Pros: de-facto React standard, mature hooks API (`useTranslation`), first-class TypeScript typed keys via `CustomTypeOptions` module augmentation, English fallback (`fallbackLng`) is a one-line config exactly matching decision 5, synchronous init with statically bundled resources (no Suspense, no loading states), huge ecosystem if needs grow (plurals, interpolation already built in), zero build-tool integration required with Vite.
   - Cons: largest runtime of the candidates (~15 kB gzip core + ~5.5 kB react binding ≈ **+20–22 kB gzip**); carries plural/ICU machinery we do not use yet.
2. **@lingui/react**
   - Pros: smaller runtime (~8 kB gzip); compiled catalogs.
   - Cons: requires a Babel/SWC macro compile step wired into Vite plus a catalog extract/compile CLI workflow — new build machinery contradicts H10; owner authors translations by editing a JSON file directly, which Lingui's compiled-catalog flow complicates.
3. **react-intl (FormatJS)**
   - Pros: standards-based ICU MessageFormat.
   - Cons: comparable or larger bundle than i18next; ICU syntax is overkill for a chrome-only string table; date/number localisation (its main strength) is explicitly out of scope.
4. **typesafe-i18n / hand-rolled context + JSON**
   - Pros: smallest possible footprint.
   - Cons: typesafe-i18n needs a generator watcher process; hand-rolled was explicitly rejected by the owner. Not pursued.

## Decision
**Option 1 — `i18next` + `react-i18next`** (current majors at install time: i18next ^25, react-i18next ^16; pin exact versions in `package-lock.json` as usual). Both locale JSON files are **statically imported and bundled** into the single main chunk — no lazy namespace loading, no backend plugin, no language-detector plugin (a 6-line localStorage read/write replaces it, honouring the "default English, no browser-detect" decision).

### Bundle-cost estimate
Current main chunk ≈ 245 kB gzip (band 243.5–246.5). Expected after adoption: **≈ 266–270 kB gzip** (+20–22 kB runtime, +1–3 kB locale JSON net of removed JSX literals). Exact number is measured and the D24 band reset to ±1.5 kB around it as the final implementation step. Bundle size deprioritized by owner 2026-08-04; the estimate exists only to keep the guard-band history coherent.

### Key naming convention
Single default i18next namespace (`translation`) — the multi-namespace feature is not used (H10). Keys are dot-path, camelCase, grouped at the top level **per feature matching `src/features/*`**, plus two shared groups:

| Top-level group | Covers |
|---|---|
| `common` | Cross-feature strings: actions (`common.action.signOut`), generic empty/loading states |
| `layout` | Sidebar nav items, header page titles (`layout.title.allRiders`), sidebar trigger aria-label |
| `auth` | LoginPage, RegisterPage, AuthShell — labels, buttons, validation messages (`auth.validation.phoneLength`) |
| `dashboards` | Dashboard, RiderDashboard, DashboardHeader, StatCard labels |
| `riders` | All/Active/Pending/Blocked riders tables, RiderDetailSheet, RiderProfileCard — headers, tabs, empty states, aria-labels |

Rules: key names describe the UI element role, never the English text (`riders.table.header.phone`, not `riders.phone_number`); interpolation uses i18next `{{name}}` placeholders; no plural suffixes this phase (out of scope).

### File layout (per ADR-0001 conventions)
A new self-contained top-level tier `src/i18n/`, mirroring the `src/mocks/` precedent for app-level infrastructure. Features may import from it (shared-tier rule); it imports from nothing in `features/`.

```text
src/
  i18n/
    index.ts          # i18next init: resources, lng from localStorage, fallbackLng "en", setLanguage helper
    i18next.d.ts      # CustomTypeOptions augmentation → typed t() keys from en.json
    locales/
      en.json         # canonical string table — English-complete, always
      ur.json         # owner-authored; missing keys fall back to en
  components/
    LanguageSwitcher.tsx   # shared tier — used by layout, dashboards and auth features
```

Alternative considered: `src/lib/i18n.ts` + `src/locales/` — rejected because it splits the init module from its data across two tiers; a single folder keeps the feature deletable/replaceable in isolation (ADR-0001 rationale).

`src/main.tsx` imports `@/i18n` for its init side effect before rendering; `tests/setup.ts` does the same so the existing 119 tests keep resolving English strings.

### Typed translation keys
Adopted — it is one declaration file (`i18next.d.ts` augmenting `CustomTypeOptions` with `resources: { translation: typeof en }`) plus `"resolveJsonModule": true` in `tsconfig.json`. Cost is near zero and it makes the strict-typecheck gate catch typo'd keys at compile time. If it ever fights the strict gate, drop the augmentation file — runtime behaviour is unchanged.

### Language switcher
A shared `LanguageSwitcher` in `src/components/` — a single toggle `Button` (shadcn, already bundled) whose label shows the *other* language name ("اردو" when English is active, "English" when Urdu is active). With exactly two languages a toggle is simpler than a select (H10) and follows the Iter-3 precedent of avoiding new Radix popper surfaces. Mounted in:
- `src/features/layout/DashboardLayout.tsx` header (right-aligned) — Admin/Operator screens
- `src/features/dashboards/components/DashboardHeader.tsx` — Rider dashboard
- `src/features/auth/pages/AuthShell.tsx` — so Login/Register are switchable before sign-in (owner to confirm; trivially removable)

### Persistence and fallback
- localStorage key: **`rydee.lang`** (sibling naming to `rydee.session`; never inside the session envelope — H7). Value: `"en" | "ur"`.
- First visit / absent / invalid value → `"en"`. No `navigator.language` detection.
- `fallbackLng: "en"`; `ur.json` may be partial at any time — untranslated keys are simply **omitted** from `ur.json` (never empty strings, which i18next would render as blank) and render in English.
- Switching language does not touch auth state, routes, or the session envelope.

### Explicitly out of scope
- **RTL layout mirroring** — no `dir="rtl"` on `<html>`/containers, no Tailwind logical-property sweep, no icon flipping. Urdu strings rely on the Unicode bidi algorithm within LTR elements.
- **Pluralization complexity** — no `_one`/`_other` key variants, no ICU. Strings that would need it stay as neutral phrasings this phase.
- **Date/number localisation** — dates stay DD/MM/YYYY, digits stay Latin (no Eastern-Arabic numerals), no `Intl` formatting changes.
- **Data values and CSV content** — rider names, areas, statuses-as-data, and all CSV export content remain untranslated (H1 wire shapes untouched).
- **Urdu webfont** — system Arabic-script fonts render Urdu in Naskh style initially; a Nastaliq webfont (e.g. Noto Nastaliq Urdu) is a separate owner decision (see plan risk register).

## Consequences
- Positive: owner edits one JSON file to translate; English fallback means the app is never broken by partial translation; typed keys guard the strict gate; strings centralised in `en.json` become the canonical UI copy inventory.
- Negative: main chunk grows ~20–22 kB gzip (accepted — bundle deprioritized 2026-08-04); every future UI string must be added to `en.json` instead of inline JSX (small ongoing tax); 119 existing tests couple to English strings, so `en.json` values must stay verbatim-identical to today's copy during extraction.
- Neutral: D24 band constants in `tests/regression/bundle-size.test.ts` reset once, mechanically; i18next's unused plural/ICU capability sits dormant; the `translation` namespace can be split later without key renames.

## Assumptions / Open questions / Risks
- **Assumption**: owner is comfortable editing `ur.json` directly with keys mirrored from the delivered string table.
- **Open**: switcher on the pre-login AuthShell — recommended, owner to confirm during live review.
- **Open**: whether a Nastaliq webfont is wanted after seeing system-font Urdu rendering.
- Risks (band churn during migration, Urdu glyph clipping in fixed-height controls, bidi punctuation in mixed table cells, test/i18n init coupling) are tracked in the plan's risk register.
